# Model card: FraudShield XGBoost fraud-risk model

_This file is regenerated by `ml/train.py`; edit `ml/report.py` to change its text._

## Purpose

Scores each card transaction with `fraud_score` (0 to 1) in the real-time authorisation path. The score only tightens the rules-engine decision: APPROVE becomes STEP_UP at 0.70 or more, STEP_UP becomes BLOCK at 0.90 or more (reason code `HIGH_FRAUD_SCORE_MODEL`). It never relaxes a rule decision. Confirming fraud and releasing false positives remain human decisions.

## Model

- Version `xgb-202610231007-64453f17`, XGBoost gradient-boosted trees (max depth 4, learning rate 0.05, early stopping at iteration 203), seed 42.
- Class imbalance handled with `scale_pos_weight` = 1 (unweighted) (chosen on validation PR-AUC).
- Explanations: exact TreeSHAP contributions from XGBoost (`pred_contribs`); the three largest positive contributions are shown to analysts in plain language.
- Served by the Flask service in `ml/app.py`; the model is loaded once at start-up. The backend gives it 150 ms; slower or failed calls fall back to the rules-only decision with `model_status = MODEL_UNAVAILABLE`.

## Data

- Training file `case_01_labelled_transactions_V1.0.csv`; out-of-time split (train txn_ts < 2026-01-01T00:00+05:30, test on or after).
- 67,085 training rows, 32,915 test rows; fraud rate 1.23% (train), 1.30% (test).
- Features (same definitions at training and decision time, case study 6.1.2): amount, local_hour, is_international, country_risk_high, distance_from_home_km, velocity_10m, velocity_24h, amount_to_avg30_ratio, new_merchant_flag, card_age_days, card_type, channel, mcc, mcc_category, merchant_risk.
- Excluded: txn_id, txn_ts, city_tier (AI-1) and all customer data (names, mobile numbers). Full card numbers never reach the model.

## Threshold rationale (AI-3)

The decision thresholds are configuration (`ai_step_up_threshold` 0.70, `ai_block_threshold` 0.90, from the case study) and can be changed by a Fraud Risk Manager without a code release. To check them we compare expected cost, where a missed fraud costs its amount and a false alarm costs INR 150:

| Operating point | Threshold | Missed fraud (INR) | False alarms | Total cost (INR) |
|---|---|---|---|---|
| step_up_0.70 | 0.7 | 3,957,542.19 | 9 | 3,958,892.19 |
| block_0.90 | 0.9 | 5,731,224.73 | 4 | 5,731,824.73 |
| cost_optimal_0.07 | 0.07 | 397,262.39 | 495 | 471,512.39 |
| baseline_any_rule | score > 0 | 2,028,738.85 | 2,299 | 2,373,588.85 |

The cost-optimal threshold on the validation slice is **0.07**. Scores between the step-up and block thresholds lead to a step-up (ask the customer) rather than a block, which keeps the cost of an uncertain score low for genuine customers. If the cost-optimal value differs materially from 0.70, the manager can adjust `ai_step_up_threshold` on the Rules page; the change is versioned and audited.

## Limitations

- The labelled file is a scenario-enriched case-study dataset; performance on live bank traffic is unknown.
- Scores are not calibrated probabilities when `scale_pos_weight` > 1; thresholds should be read as score cut-offs.
- Labelled features are pre-computed; live features are computed from stored history with the same definitions, but any definition drift between the two would reduce accuracy.
- The model does not see merchant identity, only its category and risk level.

## Governance

- Every decision stores `model_version`, the model features used and the score, so any score can be reproduced.
- Training is one command with a fixed seed: `python ml/train.py`.
- Analysts' outcomes are stored as feedback labels (`model_feedback` table) for the next training run.
